# Kairos 架构

本文记录稳定的系统边界和主要数据流。类型成员、具体 UI 布局和外部接口字段以源码为准。

## 系统概览

Kairos 是 macOS 26+ 的 Apple Silicon 菜单栏应用，由两个进程组成：

- `Kairos`：SwiftUI/AppKit 主应用，负责 UI、网络监控、场景编排、外部网络请求、用户级文件与设置。
- `KairosHelper`：通过 `SMAppService` 注册的 LaunchDaemon，以 Mach service 提供范围固定的特权 DNS 和维护操作。

主应用没有 App Sandbox。需要 root 权限的操作仍必须收敛在 Helper 的固定 XPC 接口内，不能把 Helper 变成通用命令执行器。

## 应用入口与菜单栏界面

`App/KairosApp.swift` 注册应用生命周期和菜单命令，不创建独立主窗口。`App/AppDelegate.swift` 在应用级创建唯一的 `NetworkMonitor`、`MihomoViewModel` 和 `SettingsViewModel`，注入由 `PopoverContentViewController` 内嵌 `NSHostingController` 承载的 SwiftUI 界面，并启动网络监听、Sparkle、通知和 Helper 健康检查。深度清理的 `NetworkToolsViewModel` 同样由应用级持有，执行入口拒绝重复请求，切换模块不会新建并行清理任务。

`StatusBarController` 管理 `NSStatusItem`；左键切换原生 `NSPopover` 的展开与收起，气泡位于图标下方，顶部箭头由系统定位，SwiftUI 背景延伸到原生箭头区域，内容仍遵守安全区。右键菜单导航先结束菜单追踪再打开对应模块。登录项启动时保持收起，手动启动时展开。应用维持 accessory activation policy，不在 Dock 中添加图标；Cmd+Q 收起界面，菜单“退出”和语言重启仍终止进程。

`WindowCoordinator` 持有同一个 Popover 和 hosting controller。点击外部或按 Escape 只收起显示，不销毁视图、不取消后台任务、不丢弃场景编辑或设置草稿；再次打开恢复本次运行期间的模块、工具详情、输入和结果。文件选择器、系统确认框和下拉菜单交互期间不会被外部点击监视器误关闭。该恢复行为不跨进程重启持久化。

`ContentView` 负责五个主模块：应用控制、DNS 控制、网络工具、设置和关于。一级 Tab 导航与二级返回/保存标题栏共用 60pt 高的 `PopoverPageHeader`，保持正文起点一致。`PopoverNavigationBar` 将居中的 Liquid Glass 文字胶囊与靠右的添加、刷新或保存按钮固定在气泡内顶部，右侧圆形按钮直径为 32pt，与导航选中项等高，不使用窗口标题栏或红绿灯。Escape 通过输入响应链与 SwiftUI 退出命令处理，不在底层监视器抢占输入法组字取消。工具及场景编辑在同一个气泡内部切换为详情页，返回按钮回到所属页面；场景保存继续使用右上角蓝色对号，返回明确放弃当前编辑草稿。不存在工具 sheet 或多层 Popover。IP 查询、DNS 测试和 IP 质量的输入、执行与结果在各自工具子页面内切换，新增和编辑应用/DNS 场景也进入子页面；场景编辑与工具详情共用二级页面布局，内容按自然高度展开，整个气泡（含头部与原生箭头）最高为当前屏幕可用高度的 60%。详情页返回和保存按钮复用相同的 32pt 圆形样式；工具内容保留四周留白，初始操作及进度背景限制在圆角内容区内，结果过高时内部滚动；工具容器始终保留同一个滚动视图和内容层级，避免展开或收起结果时重建输入控件。导航空间不足时胶囊内部横向滚动，保留居中位置和右侧操作区；关于页面也支持低高度下滚动。

`PopoverContentViewController` 将 SwiftUI 子视图约束在原生安全区内，关闭 hosting controller 的自动尺寸约束和重复安全区传递，外层背景覆盖箭头。`WindowCoordinator` 将内容尺寸与原生安全区分开计算，在气泡挂载后按实际安全区修正外框尺寸，避免结果展开、返回或重新打开后页面贴边。SwiftUI 根视图跟随实际承载区域布局，不提前固定为目标外框尺寸；内部页面切换一次提交完整宽高，不触发原生外框尺寸插值，打开和收起气泡仍保留系统动画。工具内容按目标宽度测量完成后再报告尺寸，不向气泡提交初始预估高度。

常态请求内容尺寸为 540×720pt（原生外框另含安全区），气泡根据内容调整高度，并限制在当前屏幕可用范围内，为系统箭头和阴影保留空间，不提供独立窗口的拖动拉伸。IP 质量结果请求宽度为 704pt，以容纳 640pt 表格及两层各 16pt 的左右间距；DNS 测试结果请求宽度为 684pt；返回工具网格或重新检测恢复 540pt，收起再展开保留当前结果尺寸。显示器配置变化或菜单栏锚点换屏时重新计算可用宽高，工具详情观察新的宽度上限并重新测量。仅屏幕宽度不足时保留表格横向滚动，详情超出可用高度时内部纵向滚动。

内核状态检测与文件操作共用路径展开规则，支持 `~/` 形式的内核路径；展开后仍执行原有 home 目录、App Bundle、可写目录和 arm64 Mach-O 安全校验。备份、恢复、替换分别保存操作结果，并记录启动时的内核目标路径；详情只展示属于当前目标的结果，同一目标返回后继续保留。

应用控制与 DNS 控制分别展示三列网络概览和场景列表，场景卡片圆点标记当前匹配状态，不表示操作已成功执行。两种场景的编辑页保留相应表单校验，保存后沿用既有持久化和网络编排路径。

设置在同一滚动页面依次呈现通用、服务、IP 质量数据源、数据、权限和日志，组标题位于卡片外，组间分割。Mihomo 应用路径、内核路径和下载源合并于服务卡片；Mihomo 配置与 API Key 使用应用级草稿，只有变更时出现顶部圆形保存按钮，保存前解析修改后的应用身份，清空应用路径后保存即解除关联。未保存草稿不参与运行或导出，导入成功后重载。API Key 保存时统一去除首尾空白和换行，运行状态、持久化与已保存草稿使用同一份规范值。通用、权限操作及日志等级即时生效，日志组可在 Finder 定位当前实际日志文件。

网络工具分为系统维护和网络检测，以三列等尺寸入口卡片呈现。DNS 清理位于第一行首格，三个内核操作位于下一行，三个检测工具并排。Mihomo 状态归入对应内核卡片和详情，顶部圆形刷新仅刷新 Mihomo 状态。DNS 清理和内核操作必须在详情内确认，执行期间禁止返回；收起气泡不取消维护。退出关联应用确认、特权调用和文件安全边界保持不变。

所有二级页面使用 `PopoverDetailPage` 固定头部、测量内容并限制整体高度，不再额外预留与头部等高的底部空白。滚动容器铺满页面宽度，内容间距放在容器内部；原生 overlay 滚动条贴页面最右侧，不挤压内容，宽度由 AppKit 按系统控件设置管理。IP 查询、DNS 测试和 IP 质量的输入、进度、开始检测及结果状态均保留内容原有内边距和 16pt 底部边缘留白，由内容决定页面高度；屏幕高度不足时缩小内容视口并内部滚动。

IP 查询使用紧凑输入布局，水平 16pt、垂直 22pt 内边距不随错误或结果增多而缩小，内容自动撑高详情，达到屏幕可用高度 60% 的整体上限后滚动。返回导航和 IP 输入框固定，仅下方结果或错误内容滚动；收起气泡继续保留查询状态。

DNS 测试采用同样的紧凑输入布局。测试期间网格进度背景铺满标题栏下方的圆角内容区，保留详情页外侧留白，不增加独立轨道边框，真实进度控制从左向右的填充长度；深蓝轨道配合低对比细网格，蓝色渐变覆盖整个已填充区域，以宽于填充区的连续周期色场从左向右变色，在线性 sRGB 中保持亮度与透明度恒定，不使用移动亮带、窄色带拼接或扫描线循环，填充前沿使用蓝青色双层柔光和中心亮芯，不绘制上下亮线，不绘制水滴、玻璃高光或胶囊外壳。前景显示 DNS 地址、当前域名序号与每个域名的轮次，取消操作统一位于子页面标题栏右上角，使用与一级刷新按钮相同的 32pt 圆形样式，进度区不承载取消按钮。轮次进度按已完成查询计算，最后一轮开始时不会提前报告 100%；结果返回后停止动画并展开结果。延迟统计只计入成功查询，整体平均延迟按成功次数加权；无成功样本时显示“无有效结果”，不把失败当作零延迟。开启减少动态效果时停用色带流动，保留进度和文字。

DNS 测试的每个进度流独立持有生产任务和结果，消费取消通过 `onTermination` 取消对应生产任务，不共享跨轮取消标志或结果数组。IP 质量取消后保留运行锁，待底层异步工作退出才开放新检测；阶段边界检查取消，进度更新不再启动脱离当前检测生命周期的任务。

IP 质量初始详情中的检测卡片高 80pt，仅显示盾牌与“开始检测”，整张卡片可点击；检测中复用 DNS 进度背景，显示百分比和当前任务，并在子页面标题栏右上角提供相同样式的取消按钮。结果自动展开，失败显示错误并保留重试。公网 IP 响应必须通过 IPv4／IPv6 校验，否则尝试备用来源；多数据源全部失败时检测失败，有基础数据但没有风险评分时显示“未获取评分”，不展示默认风险等级。对比表格直接呈现在详情内，使用直角边框；基础信息和邮件服务卡片沿用应用控制场景卡片的内边距，分数卡片保留独立样式。

界面提供 English、简体中文和繁體中文，默认跟随系统。`ApplicationLanguageController` 将用户选择保存在应用 `UserDefaults` 域，并仅在指定语言时写入 `AppleLanguages`；切回跟随系统时删除该覆盖。语言变更通过 `ApplicationRelaunchController` 重启后完整生效，该明确终止意图不会被 Cmd+Q 的隐藏窗口行为拦截。语言偏好不属于 `.kairos` 导入导出格式。

## 代码职责

- `Models/`：`Codable` 业务数据与网络响应模型，不执行 IO。
- `Views/`：页面、组件和用户交互。
- `ViewModels/`：页面状态、取消、进度和异步流程编排。
- `Services/`：系统框架、文件、网络、进程和持久化边界。
- `UseCases/IPQuality/`：IP 质量检测的领域步骤与聚合逻辑。
- `Managers/`：登录项、通知、Toast 等应用级系统服务。
- `Coordinators/`：窗口、退出确认和通知等跨视图流程。
- `Utils/`：日志、校验、超时、文件面板和设计 token。

依赖方向通常为 `View → ViewModel/Coordinator → Service/UseCase → 系统或外部边界`。新增功能应沿用这一方向，不让 View 直接承载复杂 IO，也不让底层 Service 依赖具体页面。

普通数据输入保留原生文本编辑控件，统一使用 36pt 高的圆角外框及系统语义颜色，聚焦与校验失败时显示相应边框。相邻操作按钮高 28pt，与输入框间隔 8pt、垂直居中。查询、测试、清空和密码显隐操作位于输入框旁。设置页的路径使用可编辑输入框；设置输入框均提供清空按钮，API Key 的显示切换位于输入框后，帮助入口位于标题旁。

## 网络场景

`NetworkMonitor` 使用 `NWPathMonitor` 监听路径变化，是网络自动化的应用级编排器。路径变化后，它在后台通过 `RouterInfoService` 读取本地网关 IP 和活跃接口，并经 `DNSManager` 请求 root Helper 读取当前默认网关及其 MAC。Helper 自行选择网关和主接口，仅匹配该接口的 ARP 记录，不接受客户端指定地址。主应用不能假定普通进程能读取 ARP 表；Helper 不可用时仍显示本地网关 IP，MAC 显示为不可用并记录原因。Helper 安装、修复或状态变化后会重新获取网络信息；旧的异步刷新结果不会覆盖较新的网络状态。随后在主线程更新状态并运行两套匹配引擎。

应用控制链路：

1. `SceneMatchingEngine` 按启用状态、网关 IP 和 MAC 精确匹配场景。
2. 新选择的应用保存完整路径，界面显示短名称；旧名称和 Bundle ID 引用继续兼容。`AppControlService` 先解析目标应用的 Bundle ID 与位置，再通过精确身份检查、启动和退出；退出其他应用需要辅助功能权限。退出请求发送成功不代表已经退出，只有确认目标进程终止后才记录为由 Kairos 关闭。等待超时只结束当前等待，仍保留已发送请求的进程观察；稍后退出的回执进入同一恢复记录，并按最新场景处理。
3. 离开场景后，只恢复不再受当前场景控制、且此前由 Kairos 确认关闭的应用。原本没有运行或退出失败的应用不进入恢复集合；恢复失败保留记录，按已有次数限制重试。异步执行期间网络或配置发生变化时，停止旧决策并处理最新匹配。

DNS 链路：

1. `DNSSceneMatchingEngine` 使用相同的网关 IP + MAC 规则选出第一个启用场景。
2. 当前匹配结果与已成功应用的配置分别维护；编辑 DNS 内容或接口变化会重新判断是否需要应用，不只比较场景 ID。
3. 活动接口使用 BSD 名称（如 `en0`）定位并去重，不使用可变化或重复的显示名称。Helper 只在当前网络位置的已启用服务中精确匹配 BSD 名称，不接受显示名称；没有匹配或存在多个匹配时明确报错。`DNSManager` 经 XPC 请求 Helper 设置当前活动接口的 DNS，只有操作成功才记录已应用状态；失败明确报告，并允许后续刷新重试。网络刷新开始、停止监控或规则变化使旧写入计划失效，每个尚未发送的接口请求前检查计划版本；已发送操作继续接收回执，不在刷新期间使用旧网关启动新计划。
4. 没有匹配场景时清除匹配指示，保持现有 DNS，不把 DNS 场景当作代理 profile。系统 DNS 配置变化会刷新应用级概览缓存。

## 特权 Helper 与 XPC

`DNSManager` 负责 Helper 注册、系统批准状态、版本和 bundle 指纹健康检查、必要时重新注册，以及带超时的 XPC 调用。`KairosHelper/main.swift` 建立 privileged Mach listener，并使用双方当前签名的 Team ID 和 bundle identifier 生成 reciprocal code-signing requirement；无法建立可信要求时拒绝连接或监听。

XPC 契约在以下文件各保留一份：

- `App/Services/DNSHelperProtocol.swift`
- `KairosHelper/DNSHelperProtocol.swift`

两份 selector、参数和返回类型必须同步。Helper 通过 `SystemConfiguration` 设置 DNS 和刷新接口；对于无公开 API 的操作，只执行代码中固定绝对路径的 DNS cache、ARP 和 `purge` 命令。不得接受任意命令、参数拼接或不受限文件路径。

Helper 由 Kairos 自行注册和升级，不属于 Sparkle 的运行时控制范围。修改 target 嵌入方式、LaunchDaemon plist、entitlements、bundle identifier 或签名逻辑时，必须把 app 与 Helper 作为一个发布契约验证。

## 网络工具与外部服务

- IP 查询：`IPQueryViewModel → IPQueryService → ipapi.is`。使用设置中已保存的 ipapi.is Key；未配置时采用匿名精简响应。服务边界分别解析匿名扁平格式和完整嵌套格式，再转换为查询结果；缺失项显示“—”，缺少完整坐标时不显示地图，不从使用地推断 ASN 注册地或 IP 类型。接口能力及额度以 [ipapi.is 官方文档](https://ipapi.is/developers.html) 为准。
- IP 质量：`IPQualityViewModel` 调度 `UseCases/IPQuality/`，并由 `IPDataSourceService` 并行访问可用的数据提供方。IP 类型在运行时保留独立于展示译文的分类，按来源优先级选取第一个有效分类；对比数据的持久化字段语义保持不变。ipapi.is 的 VPN 字段按服务商真值契约解析，缺失或 null 保留未知，评分与风险因子共用同一解析结果；本地合成评分遵守 0–100 范围。各来源已返回的基础资料在同一次请求中保留并聚合，风险因子包含所有已支持且提供该信息的来源，不为填补字段重复请求。来源请求失败在结果页列出具体错误，全部失败则终止检测；流媒体检测的网络、解析与超时错误向上传递，不伪装成未解锁。IPinfo 按已配置 Token 选择官方接口，未配置时选择 widget，不在接口失败后自动改用另一接口。IPWHOIS 未配置 Key 时使用 `https://ipwho.is/{ip}`，配置后使用[官方 Pro 接口](https://ipwhois.io/documentation/pro) `https://ipwhois.pro/{ip}?key=…`；凭据作为独立查询参数编码。
- ipapi.is 的 IP 查询与质量检测共享按请求身份区分的限流状态，429 后遵守服务商的 `Retry-After`，等待期间明确报错；服务商没有提供有效恢复时间时不编造期限。同一来源限流不阻断其他来源。
- DNS 基准：`DNSBenchmarkService` actor 直接向用户选择的 resolver 发送 UDP/53 A 记录查询。IP 质量使用的域名解析支持取消和截止时间，超时显式报告，不用阻塞解析包装成假超时。
- 深度清理：`NetworkMaintenanceService` 会短暂断开并恢复 Wi-Fi，经 Helper 清 DNS/ARP、刷新接口和执行 `purge`，同时直接清除 Chrome/Firefox cache。该功能会中断网络并删除用户浏览器缓存，只能由明确的用户操作触发。

`App/Info.plist` 当前允许任意网络加载。不要把现状描述为所有请求均受默认 ATS 限制；新增外部来源仍应使用 HTTPS，并在系统边界验证 URL、状态码和响应数据。

## Mihomo 内核维护

`MihomoViewModel` 聚合配置、文件、下载和关联应用进程服务。该模块不运行 Mihomo，也不管理代理规则。

- `MihomoConfigService` 保存内核路径、关联应用、GitHub Releases URL 和 asset 文件名前缀。
- `MihomoProcessService` 检查全部关联应用实例、逐个请求退出，确认全部终止后才放行内核维护；拒绝退出或超时明确报错。
- `MihomoDownloadService` 查询用户配置仓库的最新 prerelease，下载匹配的 `.gz`，按实际接收字节报告进度；总大小未知时显示不定进度。要求 asset 提供 SHA-256 digest 并校验压缩包。随后由系统 zlib 分块解压完整 gzip，校验 CRC32 和解压长度；不使用固定大小的输出缓冲区，不将截断或校验失败的数据交给内核替换流程。
- `MihomoFileService` 对现有内核创建 `.bak`，再暂存并原子替换或恢复。
- 等待关联应用退出时，回调注册、取消与完成使用同一同步状态；先取消后注册仍能结束等待，观察者与回调在锁外清理。

文件服务只接受用户 home 下的普通文件，拒绝 symlink、`.app` bundle 内路径和不可写位置，并验证替换文件是 arm64 Mach-O。GitHub asset 缺少 digest 或校验不一致时拒绝继续安装。

## 持久化与导入导出

- 应用场景：`~/Library/Application Support/Kairos/scenes.json`。
- DNS 场景：`~/Library/Application Support/Kairos/dnsScenes.json`。
- 日志：`~/Library/Application Support/Kairos/Logs/`，文件名包含日志存储器初始化时的日期，进程跨日运行时继续写入同一文件；单文件上限 10 MiB，初始化时清理超过 7 天的日志。最低记录等级默认 Debug，用户选择会持久化，后续启动与运行时均采用该设置。
- Mihomo 配置和 API Key：`UserDefaults`；API Key 当前没有使用 Keychain。
- `.kairos` 设置文件：JSON envelope，当前格式版本为 2，包含两类场景、Mihomo 配置和全部 API Key。

场景存储使用原子写入，并可从旧版 `UserDefaults` 迁移；新文件写入成功后才能删除迁移源。只有文件不存在表示初始空数据，读取、解码和写入失败都向调用方报告，不将错误转换为空场景或成功状态。

Mihomo 配置只有在偏好项确实不存在时采用默认值；存在但类型错误或解码失败时报告原错误，设置保存、维护操作和导出不能用默认配置覆盖它。修复数据后可重新加载。

设置导入先解析并验证版本、必需字段、场景身份唯一性及与编辑器一致的场景字段规则，再经用户确认提交。无效网关、DNS 或应用项在任何文件写入前被拒绝，并报告场景及字段位置。提交前根据本机的 Mihomo 应用路径重新读取 Bundle ID 和名称，不信任导出机器的身份信息；路径无效时拒绝全部写入，空路径表示解除关联。仅版本 1 保留已定义的 Mihomo 缺省兼容，版本 2 缺少配置即报错，未知未来版本拒绝导入。场景文件提交失败时恢复原文件，恢复失败同样明确报告；持久化成功后才更新运行态和成功提示。导出遇到读取错误也直接失败。导出文件包含明文凭据，应视为敏感文件。

## 更新与分发

`ApplicationUpdateController` 包装 Sparkle 2，根据构建注入的 stable、beta 或 alpha 通道决定允许的更新。appcast URL、EdDSA 公钥、签名 feed 和解压前验证开关位于 `App/Info.plist`。发布流水线、版本清单与 Homebrew/Appcast 更新见 `docs/development.md`。

## 当前已知风险与限制

- API Key 明文保存在 `UserDefaults`，也会进入设置导出文件。
- XPC 协议由两个 target 重复维护，缺少自动一致性检查。
- `DNSHelper.getDNS(interface:)` 的当前实现读取全局 DNS dynamic store，并未按传入接口过滤。

修复这些问题时应修改根因和契约，并为失败路径补充可执行验证；在修复落地前，文档和 UI 不应声称已经提供相应保障。
